# Code Review — AI Claims Processing Take-Home

**TL;DR:** The code is technically clean and shows real effort, but it misses the spec's most important requirement, over-engineers a 2-4 hour task, and carries clear signs of AI-generated code that wasn't properly cleaned up. Here's everything that needs attention.

---

## 1. You Missed the Core Requirement (Section 7)

This is the most critical failure. The spec says, in bold:

> "The important thing is that tool usage is **conditional** — the agent decides at runtime, not a hardcoded sequence."

What you built is a **deterministic 4-node pipeline**:

```
parse_documents → cross_validate → generate_message → accept_reply → [loop]
```

The agent never "decides" to use a tool. Every claim goes through the exact same sequence. The conditional edges only control *branching*, not *tool selection*. This is not the same thing.

What the spec wanted: an agent with discrete tools (e.g., `extract_fields`, `validate_vin`, `check_consistency`, `lookup_document_type`) that the agent calls *conditionally based on what it observes*. A claim with no images shouldn't invoke the image preprocessor. A claim with no VIN shouldn't call the VIN validator. The agent should reason about *what to do next*, not just follow a flowchart.

**Why this matters:** The entire point of the "tool design" section was to see how you decompose a problem into discrete capabilities and whether you can distinguish "what belongs in a tool" from "what the agent handles directly." You built a workflow orchestrator, not a tool-using agent.

---

## 2. You Changed the Status Enum Without Permission

The spec defines: `complete | incomplete | needs_review`

You implemented: `complete | incomplete | pending`

Your ARCHITECTURE.md even defends this:
> "`pending` describes ownership — the ball is in the company's court. `needs_review` only describes state."

The reasoning is fine. The action was not. You can't unilaterally rename API outputs of a spec in a take-home without noting it as a deliberate deviation and explaining the tradeoff. In a real job this would break downstream consumers. At minimum, write in the README: "I changed `needs_review` to `pending` because X, tradeoff is Y."

---

## 3. LangGraph Is Massive Overkill for This Pipeline

LangGraph is designed for complex multi-actor systems with non-trivial routing, checkpointing, and concurrent state. Your graph has 4 nodes and one loop. The equivalent code without LangGraph:

```python
def process_claim(folder_path):
    claim = parse_documents(folder_path)
    cross_validate(claim)
    for _ in range(max_rounds):
        if claim.status not in ("incomplete", "pending"):
            break
        send_message(claim)
        reply = get_reply()
        if not reply:
            break
        handle_reply(claim, reply)
        cross_validate(claim)
    return claim
```

That's 12 lines. Instead you have a compiled `StateGraph`, a `ClaimState` TypedDict with 9 keys, conditional edge registration, and graph compilation — all to express `if status == incomplete: ask customer`. This is not impressive architecture; it's complexity for its own sake. For a 2-4 hour task, LangGraph signals you spent your time on infrastructure instead of on the actual problem.

## 5. Writing to a Temp File to Immediately Read It Back

```python
# parser.py: extract_reply_fields
with tempfile.NamedTemporaryFile(mode="w", suffix=".txt", delete=False) as tmp:
    tmp.write(reply_text)
    tmp_path = tmp.name
record = TextReader().read(tmp_path, schemas, client)
```

`TextReader.read()` does exactly this:
```python
content = Path(file_path).read_text(encoding="utf-8", errors="replace")
```

So you write a string to disk, then read it back. This exists because `BaseDocReader.read()` takes a file path, but you have a string. The fix is not a temp file — the fix is that `TextReader` should accept either a path or content directly, or you extract the prompt-building logic into a shared function. The temp file is a workaround for a bad interface.

## 6. Business Logic in the Wrong Layer

`_build_customer_message` is a pure business logic function that lives in `agent.py`. It takes a `Claim` and `message_config` and returns a formatted string. By your own architectural definition, `agent.py` is the orchestration layer and `parser.py` holds claim-processing logic. This function belongs in `ClaimParser` — a node function should just call `parser.build_customer_message(claim, message_config)`.

## 7. Global Mutable State for Config

```python
# doc_reader.py
_PDF_TEXT_THRESHOLD: int | None = None

def _pdf_text_threshold() -> int:
    global _PDF_TEXT_THRESHOLD
    if _PDF_TEXT_THRESHOLD is None:
        ...read yaml...
    return _PDF_TEXT_THRESHOLD
```

This is a lazy singleton using a global variable. It's untestable (you can't reset it between tests), creates hidden module coupling, and saves you nothing — the value could just be read once in `ClaimAgent.__init__` and passed down. Or read at module import time with no function wrapper at all.

## 8. ClaimState Carries Unpersistable Objects

```python
class ClaimState(TypedDict):
    llm_client: Any   # runtime object
    chatbot: Any      # runtime object
    parser: Any       # runtime object
```

Your CLAUDE.md says: "It is fully serialisable to support future LangGraph checkpointing." This is false. LangGraph checkpointing cannot serialize Python objects like `BaseLLMClient` or `ClaimParser`. These are agent-level singletons that don't change per-claim — they should be instance variables on `ClaimAgent`, not state passed through the graph.

## 11. `raw_text` Persisted to Disk for Every Document

`DocRecord.raw_text: str | None` stores the full raw text extracted from each document, and this gets written to `claim_state.json`. For large insurance PDFs this is a significant storage blowup, and there's no functional reason to persist it — the fields are already extracted. If you need the raw text for debugging, keep it in memory only, not in the serialized state.

## 12. `ConversationRound.round` Is a Derived Field

```python
ConversationRound(
    round=len(claim.conversation_log) + 1,
    ...

```

Storing the position of an item in the list as a field on the item creates a potential inconsistency if the list is ever reordered or an item is removed. It's always `index + 1`. Either derive it at read time or remove it entirely.

The CLAUDE.md explains this as intentional, but it has no good reason. pytest's `test_*.py` convention exists specifically so any developer on any project can run `pytest` and have it work. Deviating from this makes onboarding harder for no benefit.

## 真正的改進方案

**真正解決 routing 問題** 需要這個架構：

```
node_parse_documents（保留）
       ↓
node_agent_loop（新）← 這裡換成 LLM 決定
   LLM 看到 claim state
   → 選擇呼叫 validate_vin / check_field_consistency / request_document / finalize
   → 直到 LLM 說 "done"
```

用 LangGraph 的 `ToolNode` + `create_react_agent` 可以做到，但這是實質的 rewrite。
